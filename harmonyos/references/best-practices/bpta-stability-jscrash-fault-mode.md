## Cannot read property <property-name> of undefined类案例

### 根因描述

在HarmonyOS应用开发中，“Cannot read property <property-name> of undefined”是一种常见的运行时TypeError，在错误日志中表现为如下：

```screen
Error name:TypeError
Error message:Cannot read property <property-name> of undefined
```

该错误表示代码试图从一个undefined或null的对象上访问其属性，常发生在以下场景：

* ArkTS要求变量在使用前必须赋值，变量声明后如果忘记初始化，其值就是undefined，此时访问其属性会报错。
* 变量在某个时机赋值为undefined，访问其属性会报错。
* 访问NAPI接口返回的undefined值，导致ArkTS侧读取其属性时会报错。

### 问题分析思路

第一步：提取日志关键信息

* 错误类型：TypeError。
* 错误信息：Cannot read property <property-name> of undefined。
* 报错位置：根据堆栈中的文件路径和行号定位。
* 版本信息：从ModuleName和Version获取应用版本。

第二步：定位问题代码

根据报错堆栈定位到具体的ArkTS/TS文件行号。

**说明** 

Release构建的应用包安装后，JS异常栈缺少与ETS源码行号的映射关系，堆栈信息仅显示混淆后的位置，无法溯源至原始代码行，会显示“Cannot get SourceMap info, dump raw stack”，需使用[堆栈轨迹分析](../harmonyos-guides/ide-release-app-stack-analysis.md)工具解析。

### 关键字

* 错误类型：TypeError。
* 错误信息：Cannot read property <property-name> of undefined。
* 含义解析：尝试访问的属性<property-name>所在的宿主对象当前为undefined，为非正常对象，因此无法读取属性。
* 堆栈信息作用：记录函数调用路径，用于定位错误发生的具体位置（文件、行号、列号）并追踪调用链，了解错误如何逐步触发。

ArkTS崩溃日志中的其他字段及含义，详见[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

### 案例分析

**案例一****：ArkTS侧空值访问**

**问题日志**

应用在最近任务面板执行手势操作时崩溃。崩溃日志如下：

```screen

Build info:xxxx

Module name:com.xxx.xxx
Version:1.0.0.29
VersionCode:10000029
PreInstalled:Yes
Foreground:No
Pid:2780
Uid:20020018
Reason:TypeError
Error name:TypeError
Error message:Cannot read property needRenderTranslate of undefined
Stacktrace:
Cannot get SourceMap info, dump raw stack:
    at updateGestureValue (phone/src/main/ets/SceneBoard/recent/scenepanel/recentpanel/RecentGesture.ts:51:51)
    at onRecentGestureActionBegin (phone/src/main/ets/SceneBoard/scenemanager/SCBScenePanel.ts:5609:5609)
    at anonymous (phone/src/main/ets/SceneBoard/scenemanager/SCBScenePanel.ts:555:555)
    at anonymous (phone/src/main/ets/SceneBoard/recent/RecentEventView.ts:183:183)
```

对应代码位置：RecentGesture.ts第51行，updateGestureValue()方法中尝试访问sceneContainerSessionList[this.multiCardsNum-1].needRenderTranslate.translateY时，因needRenderTranslate属性所在的上一级对象为undefined导致崩溃。

**问题代码**

```typescript
// Update the attributes related to manual effects
public updateGestureValue(screenWidth: number, recentScale: number,
  sceneContainerSessionList: SCBSceneContainerSession[]): void {
  // Calculation of the distance moved by the hand
  this.translationUpY =
    (this.multiCardsNum >= 1) ? sceneContainerSessionList[this.multiCardsNum - 1].needRenderTranslate.translateY :
      0; // Report an incorrect line number
  this.translationDownY =
    (this.multiCardsNum >= 2) ? sceneContainerSessionList[this.multiCardsNum - 2].needRenderTranslate.translateY : 0;
  this.screenWidth = this.getUIContext().px2vp(screenWidth);
  this.recentScale = recentScale;
}
```

**分析步骤**

1. 根据崩溃栈定位到RecentGesture.ts第51行，对应如下三元表达式中的属性访问：

   在访问属性链sceneContainerSessionList[index].needRenderTranslate.translateY时，触发“Cannot read property 'needRenderTranslate' of undefined”异常。该错误的直接原因是sceneContainerSessionList[index]求值为undefined，即当前索引index在数组中没有指向任何有效对象。
2. 检查数组边界保护条件。代码中仅判断了this.multiCardsNum>=1，但未校验this.multiCardsNum-1是否小于sceneContainerSessionList.length。若sceneContainerSessionList实际长度小于multiCardsNum，即使multiCardsNum>=1，访问[multiCardsNum-1]仍会得到undefined。最终分析出根因为sceneContainerSessionList数组中的元素或其needRenderTranslate属性可能为undefined。

**修复方法**

上述分析已经明确为sceneContainerSessionList的成员变量needRenderTranslate在使用的过程中可能存在为undefined的情况。对于这类问题，增加保护性判断可直接规避。具体修改方法可以如下，在访问对象前增加“?”操作符进行判断保护。

```typescript
// Update the attributes related to manual effects
public updateGestureValue(screenWidth: number, recentScale: number,
  sceneContainerSessionList: SCBSceneContainerSession[]): void {
  // Calculation of the distance moved by the hand
  this.translationUpY = (this.multiCardsNum >= 1) ?
    sceneContainerSessionList[this.multiCardsNum - 1]?.needRenderTranslate.translateY : 0;
  this.translationDownY = (this.multiCardsNum >= 2) ?
    sceneContainerSessionList[this.multiCardsNum - 2]?.needRenderTranslate.translateY : 0;
  this.screenWidth = this.getUIContext().px2vp(screenWidth);
  this.recentScale = recentScale;
}
```

**案例二：****对象被混淆后导致报错**

在官方文档的混淆问题场景中，由于开启混淆导致“Cannot read property <property-name> of undefined”错误案例详见[典型报错案例及解决方案](../harmonyos-guides/source-obfuscation-questions.md#典型报错案例及解决方案)。

### 常见易错代码预防建议

**ArkTS侧防护**

* 可选链（?.）链式属性访问obj?.prop?.subProp。
* 空值合并（??）提供默认值value??'default'。
* 空值判断（&&）使用前校验if(obj && obj.prop)。

**编码规范建议**

* 初始化优先：对象属性在使用前必须正确初始化。
* 防御性编程：跨层调用时增加空值保护。
* 避免隐式undefined：不要将对象属性主动设为undefined，使用null替代。
* 生命周期管理：确保对象在使用期间不会意外释放或置空。

总结：遇到Cannot read property错误时，首先通过日志判断问题来源（ArkTS/Native），然后根据对应分析步骤定位代码，最后采用可选链、Proxy代理等防护手段修复问题。

## <value> is not callable类案例

### 根因描述

“<value> is not callable”错误表示应用代码试图将某个非函数类型的值当作函数调用。具体而言，<value>可能为undefined、null、数字、字符串、对象等，当在其后加上括号()进行调用时，引擎发现该值没有内部[[Call]]方法，于是抛出“TypeError: <value> is not callable”。常见根因包括：

* 变量名与函数名混淆：误将变量名用作函数名，例如let result = myVariable()但myVariable()实际存储的是数字或对象。
* 对象方法不存在或未正确引用：调用对象的方法时写错了方法名，或该方法因上下文丢失而变成undefined，例如this.method()但this.method()为undefined。
* 类混淆导致方法名改变：代码混淆后，原本正确的方法名被混淆成不存在的名称，运行时找不到对应方法。
* Native模块未加载：通过NAPI调用的自定义方法，因.so文件未正确加载或符号未导出，导致调用时该值为undefined。
* 参数类型错误：传递的参数本应是函数，实际却传入了非函数类型（如数字、字符串），在函数内部被调用时报错。

### 问题分析思路

第一步：提取日志关键信息

* 错误类型：TypeError。
* 错误信息：<value> is not callable。
* 报错位置：根据堆栈中的文件路径和行号定位。
* 版本信息：从ModuleName和Version获取应用版本，便于对照对应源码。

第二步：定位问题代码

* 根据报错堆栈定位到具体的ArkTS/TS文件行号。
* 若代码为Release模式应用，需先使用报错栈还原工具[堆栈轨迹分析](../harmonyos-guides/ide-release-app-stack-analysis.md)解析还原堆栈。

第三步：查看该行代码

* 找出被调用为函数的值，例如xxx()。
* 确认是哪一个对象/变量被加上了括号调用。

第四步：溯源该值的定义

* 向上追踪该变量是如何被赋值或传入的。
* 检查类型来源：变量声明、函数参数、对象属性访问、返回值等。

第五步：判断预期类型

* 期望它是什么类型？函数？方法？还是某个对象？
* 结合业务逻辑确认应该存在的函数名或可调用对象。

第六步：验证实际类型

* 在崩溃前添加typeof日志或断点。
* 确认实际类型是否为function；若为undefined/number/object等，则需要回溯为何类型丢失。

第七步：检查作用域与上下文

* 若为对象方法，确认this指向是否正确。
* 常见于回调中解构方法，例如const { method } = obj会丢失this绑定，可改用obj.method.bind(obj)或箭头函数。

第八步：检查模块加载

* 若为NAPI或原生方法，确认对应的.so是否已正确加载。
* 调用import后，验证导出对象是否存在该方法。

第九步：考虑混淆影响

* 若开启代码混淆，查看混淆映射表。
* 确认混淆后的方法名与Native侧导出的名称一致。

### 关键字

* 错误类型：TypeError。
* 错误信息：<value> is not callable。
* 含义解析：试图以函数调用方式（即加括号()）执行一个对象，但该对象的实际类型不是函数。<value>为不可调用的具体名称。
* 堆栈信息作用：记录函数调用路径，用于定位错误发生的具体位置（文件、行号、列号）并追踪调用链。
* 定位方法：根据堆栈定位到调用<value>()的代码行，向上追溯该变量的定义和赋值过程，确认其类型来源。

ArkTS崩溃日志中的关键字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

**案例一****：number类型误调字符串方法**

**问题日志**

```screen

Timestamp:xxx

Stacktrace:

    at b entry (entry/src/main/ets/pages/test.js:18:5)
    at test1 entry (entry/src/main/ets/pages/test.js:15:5)
    at anonymous entry (entry/src/main/ets/pages/Index.ts:18:11)
HiLog:
...
```

**问题代码**

```typescript
function b(a) {
    a.trim();  // undefined is not callable;
}

export function c() {
    let a = 123;
    b(a);
}
```

**分析步骤**

1. 定位崩溃行：堆栈指向test.js:18:5，对应a.trim()调用。
2. 查看该行：被调用为函数的是a.trim()，但实际是a.trim()整体，trim()预期为函数。
3. 溯源a的值：a是b()函数的参数，在c中调用b(a)时传入a = 123，类型为number。
4. 预期类型：trim()是字符串原型方法，期望a为字符串。
5. 实际类型：typeof a === 'number'，数字没有trim()方法，因此a.trim()为undefined，对undefined加括号调用即报“trim is not callable”。
6. 根因：参数类型传递错误，将数字传给了需要字符串的函数。

**修复方法**

在传参前将数字转换为字符串：

```typescript
function b(a) {
    a.trim();
}

export function c1() {
    let a = 123;
    b(a.toString()); // Convert to string
}
```

或者修改b()函数使其兼容数字类型。

### 常见易错代码预防建议

1. 调用前检查类型，可以使用typeof或可选链，确保可调用：

   ```typescript
   function doSomething(callback) {
       if (typeof callback === 'function') {
           callback();
       }
   }
   ```
2. 避免在回调中丢失this：

   ```typescript
   // Incorrect
   const { method } = obj;
   method(); // The this keyword is incorrectly used, and the attribute may fail to be accessed in the method.

   // Correct
   obj.method();
   // Alternative
   const method = obj.method.bind(obj);
   ```
3. 为函数入参增加默认值：

   ```typescript
   // Error: If the callback is not passed or is not a function, an error will be reported.
   function doSomething(callback) {
       callback(); // TypeError: callback is not a function
   }

   // Correct: Use the default empty function (recommended).
   function doSomething(callback = () => {}) {
       callback(); // Safe, even if not transmitted, it will not report an error.
   }
   ```
4. Native方法调用前确认模块加载：

   ```typescript
   import testNapi from 'libtest.so';
   if (testNapi) {
       testNapi.add(2, 3);
   }
   ```
5. 混淆配置注意事项：

* 保留需要被动态调用的方法名：在obfuscation-rules.txt中配置-keep。
* 对于NAPI导出的方法，确保混淆规则不改变其名称。

## Cannot convert a <from-type> value to a <to-type>类案例

### 根因描述

“Cannot convert a UNDEFINED value to a JSObject”是ArkTS/JS运行时的类型转换错误，表示程序试图将一个undefined值转换为JSObject，但undefined本身不具备对象的属性和方法，无法完成转换操作。

从语言层面看，undefined在ArkTS中表示变量已声明但未赋值、属性不存在或函数没有返回值时的默认状态。而JSObject是一个具体的对象实例，undefined与其在类型上不匹配，故无法执行强制转换。值得注意的是，与标准JavaScript不同，ArkTS中对undefined和null的强制转换限制更为严格，默认情况下所有类型都是不可为空的，因此运行时一旦出现此类值传入了需要JSObject的上下文，便会抛出转换异常。

### 问题分析思路

第一步：提取日志关键信息

* 错误类型：TypeError。
* 错误信息：Cannot convert a UNDEFINED value to a JSObject。
* 报错位置：从堆栈中获取文件路径、行号和函数名，用于后续定位。
* 版本信息：通过ModuleName和Version获取应用版本，便于对照对应源码。

第二步：根据堆栈定位具体代码行号

* 根据报错堆栈定位到具体的ArkTS/TS文件行号。
* 若代码为Release模式应用，需先使用报错栈还原工具[堆栈轨迹分析](../harmonyos-guides/ide-release-app-stack-analysis.md)解析还原堆栈。

第三步：查看该行代码，找出引发异常的变量访问

* 定位到出错行，明确是哪个变量被当作对象访问了属性（例如obj.prop）或被作为函数调用（但此处更关注属性访问）。
* 确认该变量（如obj）是undefined，从而导致了异常。

第四步：溯源该变量的定义与赋值

* 向上追踪该变量是如何被声明、赋值或传入的，检查来源：
  + 变量声明（let obj = ...）。
  + 函数参数（调用时是否传入了有效值）。
  + 对象属性访问（data.result是否真实存在）。
  + 函数返回值（调用后是否可能返回undefined）。

第五步：判断预期类型

* 结合业务逻辑，明确该变量在正常运行时应是什么类型（例如应为一个对象、数组或具体类实例）。
* 若该变量本应为某个特定对象，需确认是否因数据缺失、接口返回异常等原因导致未赋值。

第六步：验证实际类型

* 在崩溃前添加防御性日志（如console.log(typeof variable)）或在调试器中打断点，确认实际类型是否为undefined。
* 若为undefined，则需进一步追究为何未被正确赋值。

第七步：区分null与undefined处理路径

* null通常表示明确的空对象引用，而undefined表示值缺失，两者在类型判断和转换行为上存在差异，应分别处理。
* 建议：在需要接收空值的场景，优先使用null或可选属性标记（?），而非依赖undefined，以便更清晰地区分“空”与“未定义”。

第八步：检查类型断言的安全性

* 若代码中使用了as关键字进行类型断言（如data as JSObject），需确认断言前的实际值类型。
* 即使进行了断言，若data本身为undefined，运行时仍会抛出转换异常，因此断言前应确保值非空，或提前进行判空处理。

第九步：排查跨语言调用（NAPI）参数传递

* 若涉及ArkTS调用Native模块，需在Native侧使用napi\_typeof()检查参数类型是否为napi\_undefined，避免无效数据传入。
* 同时检查Native模块（.so文件）是否已正确加载，导出的方法名是否与混淆后一致（若有混淆，需对照混淆映射表）。

### 关键字

* 错误类型：TypeError。
* 错误信息：Cannot convert a UNDEFINED value to a JSObject。
* 含义解析：尝试将undefined值转换为JavaScript对象（通常发生在NAPI或引擎内部操作中），但undefined本身不具备对象的属性和方法，无法完成转换。
* 堆栈信息作用：记录函数调用路径，用于定位错误发生的具体位置（文件、行号、列号）并追踪调用链。
* 定位方法：根据堆栈定位到执行转换操作的代码行，检查传入的值是否为undefined，并追溯其赋值来源。

ArkTS崩溃日志中的其他字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

### 案例分析

getPropertyNames(): string {

  const names = Object.getOwnPropertyNames(this.userInfo);

## Can not get Prototype on non ECMA Object类案例

### 根因描述

在ArkTS与Native交互开发中，若将napi\_value句柄存储于Native侧的全局变量，且未通过napi\_ref建立持久化引用，句柄将变为悬空指针。原始上下文超出生命周期或垃圾回收后，该问题会暴露。ArkTS侧访问失效句柄的属性或方法时，将触发ReferenceError异常，导致应用崩溃。常见错误场景包括：全局变量存储裸napi\_value、跨异步回调传递裸napi\_value、将napi\_value作为回调参数持久化、在多线程环境中共享napi\_value。

### 问题分析思路

第一步：提取日志关键信息

* 错误类型：ReferenceError。
* 错误信息：Can not get Prototype on non ECMA Object。
* 报错位置：从堆栈中获取文件路径、行号和函数名，用于后续定位。
* 版本信息：通过ModuleName和Version获取应用版本，便于对照对应源码。

第二步：根据堆栈定位具体代码行号

* 根据报错堆栈定位到具体的ArkTS/TS文件行号。
* 若代码为Release模式应用，需先使用报错栈还原工具[堆栈轨迹分析](../harmonyos-guides/ide-release-app-stack-analysis.md)解析还原堆栈。

第三步：查看该行代码，找出引发异常的变量访问

* 定位到出错行，明确被访问属性的变量（例如const result = testNapi.getValue();中的result）。

第四步：溯源该变量的定义与赋值

* 向上追踪该变量的来源：
  + 若是函数返回值（如testNapi.getValue()），则需检查Native模块导出的GetValue()函数的返回逻辑。
  + 若是从全局/静态变量读取，需追踪该全局变量在Native侧的赋值过程（例如在Add函数中创建的数组）。
  + 注意该变量是否经过多层传递（如从异步回调、页面状态等），确认其初始赋值路径。

第五步：判断预期类型

* 结合业务逻辑，明确该变量在正常情况下应为何种类型（例如应为一个Array、Object或具体的类实例）。
* 若预期为Native侧创建的JS对象（如通过napi\_create\_array()生成），则需确认该对象在返回时是否仍然有效。

第六步：排查跨语言调用（NAPI）参数传递与生命周期管理

* 检查Native模块源码中的导出函数（如GetValue()），确认其返回的napi\_value是否直接使用了全局/静态变量存储，而未通过napi\_create\_reference()创建持久引用。
* 追踪该全局变量的赋值来源（如Add中创建的数组），确认是否存在以下问题：
  + 在异步操作或回调中传递了原始的napi\_value，但异步完成时该值已被垃圾回收。
  + 在多线程环境下共享napi\_value，而napi\_value并非线程安全。
  + napi\_handle\_scope使用不当，导致局部句柄在作用域关闭后引用计数减少，外部持有的值变为悬空指针。
* 验证ArkTS侧是否存在触发垃圾回收的操作（如ArkTools.hintGC()、页面销毁、异步任务完成等），这些操作会暴露悬空指针。
* 确认是否缺少持久引用机制：若无napi\_create\_reference()，则根因即为Native侧未正确延长对象生命周期。同时，在Native入口处可使用napi\_typeof()检查传入参数是否为napi\_undefined，并确认.so模块是否正常加载且导出方法名与混淆后一致（若有混淆需对照映射表）。
* 最终修复方案：在Native侧为需要长期持有的对象创建napi\_reference，并在适当位置释放，确保ArkTS侧访问时句柄始终有效。

### 关键字

* 错误类型：ReferenceError。
* 错误信息：Can not get Prototype on non ECMA Object。
* 含义解析：尝试获取一个非ECMAScript对象的原型（prototype），通常发生在跨语言调用或操作原生对象时，该对象不支持原型链操作。
* 堆栈信息作用：记录函数调用路径，用于定位错误发生的具体位置（文件、行号、列号）并追踪调用链。
* 定位方法：根据堆栈定位到触发原型访问的代码行，检查操作的对象是否为合法的JS对象，避免对原生句柄或C++对象进行原型操作。

ArkTS崩溃日志中的其他字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

```typescript
static napi_ref objValuesRef = nullptr;

static napi_value Add(napi_env env, napi_callback_info info) {
    // ... create jsArray ...
    // Create persistent reference (refcount=1)
    napi_create_reference(env, jsArray, 1, &objValuesRef);
    // ... return result ...
}

static napi_value GetValue(napi_env env, napi_callback_info info) {
    napi_value obj;
    napi_get_reference_value(env, objValuesRef, &obj);
    return obj;
}

// Release reference when module unloads or no longer needed
// napi_delete_reference(env, objValuesRef);
```

### 常见易错代码预防建议

1. 严格区分napi\_value与napi\_ref的使用场景：
   * napi\_value：仅作为局部句柄使用，生命周期仅在当前函数调用栈及HandleScope内。绝对禁止将其存储到全局/静态变量或跨线程传递。
   * napi\_ref：当需要长期持有JavaScript对象（如跨异步操作、全局缓存）时，必须使用napi\_create\_reference()创建持久引用，并在对象不再需要时调用napi\_delete\_reference()释放。
2. HandleScope的正确使用：
   * 打开HandleScope后创建的所有局部napi\_value在关闭作用域后将失效。若需要将其中某个对象返回给调用方，应确保在关闭作用域前返回该值（引擎会将其提升到外层作用域），但若需存储到全局，仍需转为napi\_ref。
   * 避免在同一个函数中打开多个HandleScope，除非明确需要控制内存。
3. 异步操作中的引用管理：
   * 在发起异步任务（如使用工作队列、线程池）前，对需要传递的JavaScript对象创建napi\_ref。
   * 在异步任务完成回调（通常仍在NAPI线程）中，通过napi\_get\_reference\_value()获取对象，使用后及时释放引用。
4. 多线程环境禁止共享napi\_value：
   * napi\_value并非线程安全，不能在不同线程间直接传递。若需跨线程使用JavaScript对象，应在线程中创建napi\_ref，并通过线程安全函数如napi\_create\_threadsafe\_function()或序列化方式传递。
5. 编码规范与自动化检测：
   * 在代码规范中明确禁止将napi\_value赋值给全局/静态变量。
   * 可定制静态检查工具（如Clang-Tidy、ESLint插件）扫描此类违规赋值，并提示使用napi\_ref。
   * 代码审查时重点关注HandleScope的闭合位置及全局napi\_value的使用。

通过以上规范和实践，可有效避免因napi\_value生命周期管理不当引发的“Can not get Prototype on non ECMA Object”类崩溃问题。

## Unexpected <text> in JSON类案例

### 根因描述

在HarmonyOS应用开发中，使用JSON.parse()解析字符串时，若传入的字符串不符合JSON规范，会抛出SyntaxError类型的运行时异常，错误信息通常以“Unexpected xxx in JSON”形式出现，在错误日志中通常表现为如下：

```screen
Error name:SyntaxError
Error message:Unexpected XXX Text in JSON at position XXX, XXX
```

### 问题分析思路

第一步：捕获异常并提取错误信息

* 获取异常对象，提取错误消息（如“Unexpected end Text in JSON at position 15”）和位置编号（position值）。
* 结合堆栈信息定位到执行JSON.parse()的具体代码行，确认传入的原始字符串内容。

第二步：根据错误消息关键字判断违规类型

* 若包含“Unexpected end”且位置在末尾附近，可能是对象/数组未闭合。
* 若包含“Unexpected Number”且位置在数字处，可能数字格式异常（前导零或非法字符）。
* 若包含“ParseLiteralTrue Fail”或“ParseLiteralFalse”，多数为布尔值拼写错误（如ture）。
* 若包含“Unexpected Text”且位置在字符串值处，通常为字符串缺少结束引号。
* 若位置指向深层嵌套区域，需检查括号层级是否完整。

第三步：对照常见原因采取修复措施

* 对象未闭合：补全缺失的}，确保所有键值对完整，例如{"name":"value","age":18}。
* 数组未闭合：补全缺失的]，例如[1,2,3,4,5,6,7,8]。
* 字符串未闭合：在字符串值末尾添加双引号，例如{"name":"verylong"}。
* 数字含非法字符：仅保留纯数字，去掉前导零（除非数字就是0），如{"value":123}或{"value":"0123"}。
* 布尔值错误：统一使用小写true/false，例如{"flag":true}。

第四步：处理深层嵌套与括号匹配

* 对于层级较深的JSON（如嵌套多层对象），使用编辑器括号高亮或格式化插件逐层校验。
* 常见错误是漏写某层}，导致后续属性被错误归属，需借助JSON验证工具进行结构检查。

第五步：验证修复结果并增强健壮性

* 使用在线验证器（如jsonlint）或本地try-catch包裹JSON.parse()进行测试。
* 若业务允许，可在解析失败时给出友好提示，避免应用崩溃。同时可记录原始字符串，便于后续复现分析。

**说明** 

从**API version 24**开始，系统增强了错误日志：会输出匿名化的JSON字符串片段和错误位置（零基索引），以帮助开发者高效定位异常。但需注意，Worker和TaskPool目前尚不支持打印这些日志信息。

**脱敏规则**

由于JSON字符串可能包含用户敏感信息，报错日志输出的字符串片段按以下规则匿名化：

* **截取范围**：以错误位置为中心，截取前后各15个字符；若任一侧不足15个字符，则按实际长度截取。
* **结构字符保留**：以下字符保持原样，不做脱敏：{ } [ ] " : , \r \t \n 空格符。
* **非结构字符脱敏**：其余字符按“保留一位、脱敏一位”的方式从左到右交替处理。首个非结构字符保留原文，后续第2、4、6……个非结构字符替换为\*。

### 关键字

* 错误类型：SyntaxError（JSON解析错误，具体信息含Unexpected end/Unexpected Number/Unexpected Text等）。
* 错误信息：如Unexpected end Text in JSON at position 15，包含位置编号及匿名化字符串片段（如e":"v\*l\*e","a\*e"）。
* 含义解析：传入JSON.parse()的字符串不符合JSON语法规范，常见原因包括：对象/数组未闭合、字符串缺少结束引号、数字含前导零或非法字符、布尔值拼写错误等。
* 堆栈信息作用：指明出错的文件名、行号、列号（如.ets:37:18），用于定位调用JSON.parse()的位置。
* 定位方法：根据堆栈定位到调用行，获取原始字符串内容，结合错误信息中的位置编号检查对应字符，对照JSON规范修正格式。

ArkTS崩溃日志中的其他字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

**案例一****：Unexpected end Text in JSON（JSON字符串提前结束）**

**修复方法**

```typescript
let str1 = "{\"name\":\"value\",\"age\":21}";
JSON.parse(str1)
```

### 常见易错代码预防建议

1. 始终使用try-catch保护JSON.parse()：

   ```typescript
   try {

       console.error(`JSON parsing failed: ${e.message}, Original string: ${inputStr}`);
       // Provide downgrade processing or report exceptions.
   }
   ```
2. 避免手写JSON字符串，使用对象+JSON.stringify()：

   反例：

   ```typescript
   let str = "{name: 'value'}";           // The key is not enclosed in double quotation marks, and the value is enclosed in single quotation marks.
   let str = "{\"value\":0123}";          // error prone
   ```

   正例：

   ```typescript
   let obj = { name: "value", value: 123 };
   let str = JSON.stringify(obj);         // Automatically generate valid JSON
   let parsed = JSON.parse(str);
   ```
3. 对外部数据（网络、文件、用户输入）进行预处理和校验：
   * 接收后端数据时，确认实际响应体内容。若后端返回非标准格式，需要先判断再解析。
   * 使用第三方JSON校验库进行快速验证（调试阶段）。
   * 当字符串可能被截断时，检查字符串长度或完整性标志。
4. 常用JSON转义规则如下表所示：

   | 需要转义的字符 | 正确写法 |
   | --- | --- |
   | 双引号 " | \" |
   | 反斜杠 \ | \\ |
   | 换行符 | \n |
   | 回车符 | \r |
   | 制表符 | \t |

总结：“Unexpected xxx in JSON”异常的根本原因是字符串不符合JSON规范。通过分析日志中的错误类型、位置、匿名片段和调用栈，可以快速定位到问题代码。预防核心在于“避免手写，多用JSON.stringify()；解析前加try-catch；对外部数据保持怀疑”。遵循上述指导，可显著降低此类崩溃的发生率。

## Stack overflow类案例

### 根因描述

Stack Overflow（栈溢出）是指程序运行时，调用栈（Call Stack）所使用的内存空间超出了系统为该线程分配的栈容量上限，导致程序崩溃的异常现象。在ArkTS开发中，该异常通常表现为Error message：Stack overflow!

### 问题分析思路

第一步：观察异常信息快速识别类型

* 当应用崩溃时，首先查看异常信息。
* 若报错内容包含Stack overflow，则可直接判定为栈溢出问题。

第二步：分析调用栈模式

* 递归失控特征：调用栈中出现大量重复的相同函数调用（例如funcA→funcA→funcA...），层数达几十上百层，基本可确认为递归失控。
* 深度嵌套特征：调用栈中出现大量if-else、as转换或括号嵌套的重复模式，表明可能存在过度嵌套导致栈溢出。

### 关键字

* 错误类型：RangeError。
* 错误信息：Stack overflow!。
* 含义解析：函数调用栈超出限制，通常由递归失控（无终止条件）或过深的嵌套调用（如大量if-else、as转换等）导致。
* 堆栈信息作用：记录函数调用路径，定位错误发生时的具体位置（文件、行号、列号）并追踪调用链。
* 定位方法：观察堆栈中是否有重复的相同函数调用（如funcA→funcA→...）或深度嵌套模式，据此检查递归终止条件或优化嵌套逻辑。

ArkTS崩溃日志中的其他字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

### 案例分析

**问题日志**

```screen
Reason:RangeError
Error name:RangeError
Error message:Stack overflow!
Stacktrace:
Cannot get SourceMap info, dump raw stack:
    at factorial (entry|entry|1.0.0|src/main/ets/pages/Index.ts:90:25)
    at factorial (entry|entry|1.0.0|src/main/ets/pages/Index.ts:90:25)
    at factorial (entry|entry|1.0.0|src/main/ets/pages/Index.ts:90:25)
    at factorial (entry|entry|1.0.0|src/main/ets/pages/Index.ts:90:25)
...
```

**问题代码**

```typescript
function factorial(n: number): number {
    return n * factorial(n - 1);
}
```

**分析步骤**

1. 根据崩溃栈定位到Index.ts第90行，对应factorial()函数调用，结合[堆栈轨迹分析](../harmonyos-guides/ide-release-app-stack-analysis.md)解析行号信息。堆栈显示多次重复的factorial()调用记录，且每一层调用参数未发生递减或终止条件未满足，初步判断为递归未正确终止导致的栈溢出错误。
2. 检查factorial()函数实现逻辑，发现该递归缺少基准条件（n <= 1时返回1）。当n为正整数时，会无限递归直至调用栈溢出；若n为负数，则n-1始终为负，同样无法终止。

**修复方法**

1. 根本原因为递归函数缺少终止条件，或终止条件逻辑错误（如条件永远不会满足）。
2. 修改factorial()函数，增加基准条件：

   ```typescript
   function factorial(n: number): number {
       if (n <= 1) return 1;   // Handle 0, 1 and negative numbers (can be changed to absolute value or throw error as needed)
       return n * factorial(n - 1);
   }
   ```

### 常见易错代码预防建议

1. 递归函数要始终确认终止条件：递归缺少基准条件（base case），或基准条件永远无法满足，导致调用栈溢出。

   预防措施：

   * 编写递归前先明确：输入什么值时递归结束。
   * 使用if (n <= 1) return 1;等显式终止逻辑。
   * 对于可能过深的递归（如遍历大文件树），考虑改用迭代（循环 + 栈/队列）或尾递归优化（若环境支持）。
   * 添加递归深度计数器，超过阈值时抛出明确错误。
2. 异步错误未捕获：async函数内的await未包裹try-catch，或Promise未加.catch()，导致失败。

   预防措施：

   * 顶层异步调用使用catch()或全局使用errorMessage。
   * 在async函数内使用try-catch包裹所有await。

## <name> is not initialized类案例

### 根因描述

“<name> is not initialized”错误的根本原因是模块间循环依赖，导致变量在访问时尚未被初始化。ArkTS/ECMA规范采用深度优先顺序加载模块。若存在循环依赖（如A→B→A），加载器会先标记A为“加载中”，然后加载B，B依赖A时发现A状态为“加载中”，直接返回未完成的A模块。此时若B中的全局代码或静态块立即使用了A的导出变量，该变量尚未完成赋值，就会触发“ReferenceError: <name> is not initialized”。这类问题的本质是模块/类职责边界不清、耦合度过高，导致初始化顺序冲突。

### 问题分析思路

遇到“<name> is not initialized”崩溃时，按以下步骤排查：

1. **确认错误类型**

   日志中Error name: ReferenceError、Error message: <name> is not initialized明确指向变量未初始化问题。
2. **开启循环依赖检测开关**（无需重启设备）

   ```screen
   开启：hdc shell param set persist.ark.properties 0x2000105c
   关闭：hdc shell param set persist.ark.properties 0x0000105c
   ```

   开启后复现问题：

   * 若仍报“<name> is not initialized”则确认存在循环依赖。
   * 若出现其他第一现场错误（如明确的循环依赖警告）则按实际错误修复。
3. **定位循环链路**

   分析Stacktrace中的文件调用关系，查找模块间的相互导入。可使用ESLint规则[@security/no-cycle](../harmonyos-guides/ide_no-cycle.md)或手动梳理依赖图。
4. **检查全局/静态代码块**

   重点排查以下位置是否使用了未初始化完成的导入变量：

   * 模块顶层代码（export let x = ... 右侧表达式）。
   * 类的static初始化块、静态属性默认值。
   * 立即执行的函数表达式。

### 关键字

* 错误类型：ReferenceError。
* 错误信息：<name> is not initialized（<name>为变量名，混淆代码中可能为短符号如z822）。
* 含义解析：代码尝试访问一个尚未完成初始化（或未声明）的变量。
* 堆栈信息作用：记录函数调用路径，定位错误发生的具体位置（文件、行号、列号）并追踪调用链。
* 定位方法：根据堆栈定位到访问该变量的代码行，向上查找该变量的声明和赋值语句，确认是否在访问前已正确初始化。

ArkTS崩溃日志中的关键字段及含义，可查看[日志规格](../harmonyos-guides/jscrash-guidelines.md#日志规格)。

### 案例分析

**问题日志**

```screen

Fingerprint:xxx
Timestamp:xxx

Version:1.1.10.210
VersionCode:101010210

    at func_main_0 (entry|entry|1.0.0|src/main/ets/engine/en/KbdEnLayoutUtils.ts:0:3016)

```

**问题代码**

```typescript
import { Animal } from './XXXIsNotInitializedCase1'

export let a = "this is A";

export function A() {
  return new Animal;
}
```

```typescript
import { a } from './XXXIsNotInitializedCase'

export class Animal {
  static {
    console.log("this is in class");
    let str = a; // a is not initialized
  }
}
```

**分析步骤**

1. 开启循环依赖检测开关（hdc shell param set persist.ark.properties 0x2000105c）。运行应用，观察崩溃信息是否有发生变化，若仍报“<name>is not initialized”则存在循环依赖。
2. 由于XXXIsNotInitializedCase1导出的A依赖Animal（来自XXXIsNotInitializedCase），而后者在静态初始化时反向依赖前者的a，导致循环引用。依赖链为XXXIsNotInitializedCase1→XXXIsNotInitializedCase→XXXIsNotInitializedCase1，引发未初始化加载失败问题。
3. 模块在首次被导入时，按深度优先顺序执行顶层代码。当遇到循环依赖时，引擎先开始加载XXXIsNotInitializedCase1，执行其顶层代码（包括导出a），但由于XXXIsNotInitializedCase1的导入会触发XXXIsNotInitializedCase的加载，此时a尚未完成赋值（XXXIsNotInitializedCase1的执行被挂起，等待XXXIsNotInitializedCase完成）。随后在加载XXXIsNotInitializedCase时，执行其顶层代码（包括Animal类的static块），而Case中的导入a会去读取XXXIsNotInitializedCase1的导出，但此时XXXIsNotInitializedCase1的a还未被赋值为“this is A”（因为XXXIsNotInitializedCase1的执行仍处于挂起状态），因此a的值为undefined（或未初始化标记），导致访问时报错。

**修复方法**

```typescript
import { Animal } from './XXXIsNotInitializedFix1'

export let a = "this is A";

export function A() {
  return new Animal;
}
```

```typescript
import { a } from './XXXIsNotInitializedFix'

export class Animal {
  static {
    console.log("this is in class");
  }
  str = a; // Modification point
}
```

避免在顶层代码、静态块中直接使用可能循环依赖的导入变量。将依赖推迟到实例化阶段（如构造函数、实例属性）或通过函数懒加载。

### 常见易错代码预防建议

**建议一：建立无循环依赖的模块结构**

* 提取公共依赖：将多个模块共同依赖的变量或类抽离到独立文件（如common.ts/types.ts），避免相互引用。
* 使用依赖注入：通过构造函数或参数传递依赖，而非模块顶层直接引用。

```typescript
// Counterexample: A ↔ B circular dependency.
// Positive example: Introduce C as a common module.
// C.ets
export let sharedData = "base"
// A.ets
import { sharedData } from './C'
// B.ets
import { sharedData } from './C'
```

**建议二：****延迟加载（lazy import）**

将可能产生循环依赖的变量访问推迟到运行时，而非模块加载阶段，具体使用可参考[延迟加载（lazy import）](../harmonyos-guides/arkts-lazy-import.md)。

**总结**

“<name> is not initialized”本质是模块初始化顺序冲突，最佳解决路径为：

1. 设计层面：消除循环依赖/提取公共模块/依赖注入。
2. 编码层面：延迟初始化/避免静态块/顶层使用导入变量。
3. 工具层面：ESLint循环检测/开发设备运行时开关。
4. 验证层面：复现并确认无“<name> is not initialized”错误后关闭开关。

通过以上组合策略，可系统性地预防和解决该类异常问题。
